# deslop-docs：把文档写成像工程师写的

文档的敌人不是文采不足，是三件东西：类型混装、句子含糊、模板套话。按顺序解决。

风格层（`deslop`）管语感，这一层管结构与精确。两者冲突时，文档正确优先。

## 一、先判类型，只做一件事

Diátaxis 四类，混装是最大的结构病。落笔前先写一句话回答「读者读完要能做什么」，答案决定类型：

| 类型 | 读者状态 | 只回答 | 判断口诀 |
|---|---|---|---|
| 教程 Tutorial | 不会 | 怎么从零做出一件能跑的东西 | 有可运行结果，回避岔路 |
| 操作指南 How-to | 会一点 | 怎么解决这一个具体问题 | 一步一动作，不教原理 |
| 参考 Reference | 会用，来查 | 这个参数/命令/字段是什么 | 穷尽、格式一致、不叙事 |
| 解释 Explanation | 想懂 | 为什么这样设计、有哪些取舍 | 可以长，但不能有步骤 |

判错的典型症状：参考章节里出现「首先你需要安装」；教程里塞三种方案；操作指南里讲起了协议原理。发现混装，先拆文件，再改句子。

## 二、结构骨架（照抄，别自由发挥）

**教程**：这一步能做出什么 → 前置条件（版本、权限、耗时）→ 编号步骤（每步一条命令、一条预期输出）→ 验证（怎么知道成功了）→ 下一步去哪儿。不写「常见问题」，那是操作指南。

**操作指南**：目标一句话 → 适用条件 → 步骤 → 完成后如何确认 → 相关链接。

**参考**：条目名 → 类型/默认值/取值范围 → 行为说明 → 一个最小示例。所有条目字段顺序必须一致；缺一个参数就是缺陷，不是精简。

**解释**：问题是什么 → 现状为什么不够 → 方案与代价 → 什么情况下不该用它。

**README** 是另一件事：一句话说清这是什么 → 安装 → 最小可用示例 → 配置表 → 指向更深的文档。不写「功能特色」清单，不写路线图展望。

## 三、句子与用词（技术写作的硬约束）

- 主动语态、现在时、动词开头。「运行 `pnpm build`」而不是「`pnpm build` 需要被运行」。
- 第二人称指读者（你），第三人称指系统（该命令、服务、进程）。避免「我们」，除非真的在说团队做过什么。
- 一个句子一个意思，平均 15–25 字，超过 40 字拆开。句长要有起伏，不要每句都同长。
- 术语一次定，全书不变。同义词轮换（接口/端点/API/服务 混用）会让读者以为是四个东西。
- 数字带单位与量级：「延迟 120 毫秒」不是「延迟很低」。
- 条件与后果写全：「删了这个字段，旧客户端会读不到数据」，不要写「请谨慎操作」。
- 不承诺无法验证的事。写不出来的地方留 `[待补: 需要实测]`，不要用形容词填空。

**中文排版**：中文与英文/数字之间加空格；全角标点，但代码与路径用反引号包住并保持原样；不要「进行」「的的」堆叠（「进行配置」→「配置」）；避免翻译腔的「被」字句和「使得」。

## 四、文档体裁特有的 AI 味（逐条核）

这些在正文语感里不一定显眼，但在文档里一眼就露：

1. **Key Features / 核心特性** 列表——四到六条名词短语，每条都无法验证。删掉，改成一句话说清它做什么。
2. **What it does / Why it's valuable / Who it's for** 三段式——同一模板重复到每个模块。合并成一句。
3. **结尾复述**：「以上我们介绍了……。希望本指南对你有帮助。」文档不需要告别。
4. **加粗当标题、冒号标签行**：`**速度：** 快` 这种伪表格。真需要对比就用表格，否则写成句子。
5. **过度分点**：两句话能说清的事拆成五个 bullet。分点只用于并列、可枚举、顺序无关的项。
6. **徽章与营销词**：seamless、robust、powerful、effortless、cutting-edge、enterprise-grade。删。
7. **免责垫话**：「需要注意的是」「值得一提的是」「需要注意的是」——直接说事。
8. **聊天残留**：Certainly、Great question、Here is a polished version、[Your Name]、引用标记 `[1]` `turn0search0`。
9. **破折号节奏**：文档里一段最多一个破折号，且只用于插入语。
10. **假装完整的示例**：省略号、`...`、只给一半的 YAML。示例要么能跑，要么明确标注片段。
11. **标题大小写混乱**：句首大写制（sentence case）统一到底，不要标题里 Each Word Capitalized。
12. **链接文字**：「点击这里」「详见此处」。用目标的名字做链接文字。

## 五、删减（文档臃肿五类）

重复内容、能合成散文的长列表、同一概念的两个示例、可删一半的冗长描述、每个模块都一样的模板结构。改法是外科手术式的：保留信息，压缩表达，不动事实。

删之前问一句：「删掉这句，读者会做错什么？」不会做错就删。

## 六、交付前自检（12 项）

- [ ] 类型单一，没有混装
- [ ] 第一段说清了读者读完能做什么
- [ ] 前置条件（版本/权限/耗时）写全
- [ ] 每个命令可复制粘贴，没有占位符漏填
- [ ] 示例完整可运行，或明确标注为片段
- [ ] 术语全书一致，没有同义词轮换
- [ ] 无 Key Features 段、无结尾复述、无免责垫话
- [ ] 分点只用于可枚举项，散文段没有被拆碎
- [ ] 标题句首大写制统一，没有加粗当标题
- [ ] 链接文字是目标名，不是「这里」
- [ ] 中文与拉丁字符之间有空格，标点统一
- [ ] 数字带单位，断言有出处或实测

## 七、能自动化的部分别靠人眼

- **Vale**（`errata-ai/vale`）+ 官方风格包 `errata-ai/Google` 或 `errata-ai/Microsoft`：把风格指南变成 CI 里能挂的规则，术语表放 `Vocab/`，自定义规则写 `accept.txt`。
- **markdownlint**：标题层级、列表缩进、代码块语言标注。
- **textlint**：中文规则集（标点、空格、重复词）。
- 本插件的 `deslop_scan` 只评估语气，不评估文档正确性；文档的机械检查交给上面三个。

一段能直接用的 `vale.ini`：

```ini
StylesPath = styles
MinAlertLevel = suggestion
[*.md]
BasedOnStyles = Vale, Google
Google.Headings = NO   # 允许句首大写制与自有标题风格
```

## 八、与 deslop 的分工

长文、博客、邮件、对外文案走 `deslop` 三遍法。文档、README、API 参考、RFC 走这一层：先定类型与骨架，再收句子，最后清模板。两边都改时，先文档结构，再语感，顺序不能反——结构错了，句子再干净也是白改。
